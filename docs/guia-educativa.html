Esta guía está pensada para que un profesor pueda explicar Nexus-Core en clase y para que el alumnado entienda qué hace, cómo está construido y, sobre todo, por qué se tomaron cada una de las decisiones. 1. Qué es Nexus-Core

Nexus-Core convierte un servidor Linux en un centro de control para vigilar y administrar otras máquinas. Desde una única página web se puede ver la telemetría del sistema, gestionar contenedores Docker, revisar servicios, lanzar un escaneo de la red local, consultar puertos, actualizaciones y discos, recibir alertas y ejecutar acciones con confirmación.

La plataforma nace como Trabajo Fin de Grado de SMR, pero está construida como un producto real: un hub central, agentes que se instalan en otras máquinas y una interfaz que funciona en local y a través de Internet.

La idea en una frase: un panel único, ligero y comprensible, que convierte datos sueltos (CPU, RAM, servicios, contenedores, red) en decisiones y en acciones auditables.

1.1 El problema que resuelve

En un aula o en una pequeña infraestructura, la información está repartida: métricas en una herramienta, servicios en otra, contenedores en la terminal, la red en un escaneo manual y las alertas en el correo. Nexus-Core reúne esas señales en un solo lugar y añade tres cosas que suelen faltar en un TFG:

  1. Contexto: no solo muestra un número, explica si está bien, regular o mal.
  2. Acción controlada: permite actuar (reiniciar un servicio, desplegar un contenedor) con lista blanca, confirmación y auditoría.
  3. Trazabilidad: cada acción queda registrada; el administrador puede reconstruir qué pasó.

1.2 Objetivos de diseño

Objetivo Decisión
Funcionar en una máquina modesta (Raspberry Pi, VM) Backend Python ligero, SQLite, frontend sin compilación
No depender de la nube Todo el núcleo funciona en local; Internet es opcional
Poder vigilar máquinas detrás de NAT El agente inicia la conexión hacia fuera; no se abren puertos
Ser entendible para un alumno Código modular, nombres explícitos, documentación y auditoría
No convertir la IA en un riesgo La IA propone; una persona confirma acciones sensibles

2. Arquitectura general

Nexus-Core tiene tres piezas:

┌────────────────────┐        HTTPS (saliente)        ┌──────────────────────────┐
│  Navegador / móvil │ ─────────────────────────────▶ │  Hub Nexus-Core          │
│  del administrador │                                │  FastAPI + SQLite        │
└────────────────────┘                                │  Panel web + API         │
                                                      └────────────┬─────────────┘
                                                                   │ long-poll / comandos
                                      ┌────────────────────────────┼───────────────────────────┐
                                      │                            │                           │
                              ┌───────▼────────┐          ┌────────▼───────┐          ┌────────▼───────┐
                              │ Agente Linux 1 │          │ Agente Linux 2 │          │ Agente Windows │
                              │ systemd        │          │ Docker         │          │ (limitado)     │
                              └────────────────┘          └────────────────┘          └────────────────┘
  • Hub: servidor central. Ejecuta el panel, la API, la base de datos, el motor de alertas, los monitores y el despachador de comandos.
  • Agentes: procesos instalados en cada máquina vigilada. Recogen métricas y ejecutan herramientas bajo demanda. Solo abren conexiones salientes hacia el hub.
  • Navegador: consume el panel. No necesita instalar nada.

2.1 Por qué hub + agentes

Un panel que “entra” en cada máquina necesitaría abrir puertos, configurar cortafuegos y gestionar credenciales en cada host. El modelo de agente invierte la dirección: cada máquina abre una conexión saliente al hub. Esto permite funcionar detrás de NAT, en redes de aula o en un servidor doméstico sin IP fija. Es el mismo patrón que usan herramientas comerciales de monitorización.

2.2 El protocolo agente-hub

  1. Alta (enroll): el agente presenta un token de enrolamiento y recibe un token propio para ese host. El token de enrolamiento es un secreto de alta; el token del host identifica a la máquina en cada petición.
  2. Latido (heartbeat): cada pocos segundos el agente informa de que sigue vivo y envía su inventario (contenedores, servicios, versión).
  3. Long-poll de comandos: el agente mantiene una petición abierta esperando órdenes. El hub responde en cuanto hay una herramienta que ejecutar, sin que el agente tenga que sondear agresivamente.
  4. Resultado: el agente devuelve done o error. El hub guarda el comando y su resultado.

Por qué long-poll y no WebSocket: el long-poll es más simple de operar (HTTP normal, proxies, TLS) y suficiente para una herramienta de administración. Un WebSocket añadiría estado y reconexiones que este proyecto no necesita.

2.3 Qué ocurre cuando el hub está apagado

Los agentes siguen funcionando: reintentan con una espera que crece de 2 a 30 segundos. No se pierde la configuración ni los servicios de la máquina. Cuando el hub vuelve, los agentes reconectan solos. Las métricas del periodo de caída no se backfillean (el agente no guarda un búfer histórico); es una limitación consciente y una posible mejora futura.

3.1 Alertas: del dato a la decisión

Una alerta no es “CPU al 90 %”. Una regla define un umbral, una duración mínima para evitar falsos positivos, un umbral de recuperación (histéresis) y unos canales de notificación. El estado pasa por ok → aviso → crítico → recuperada; el administrador puede reconocerla o silenciarla durante un mantenimiento.

Por qué la histéresis: sin ella, un valor que oscila alrededor del umbral generaría decenas de eventos. Con ella, la alerta se abre cuando se cruza el umbral y se cierra solo cuando baja del umbral de recuperación.

3.2 Monitores y página de estado

Los monitores comprueban HTTP, TCP y certificados SSL. Su resultado alimenta una página pública de estado y un endpoint de métricas para Prometheus. Es una separación deliberada: la telemetría del host no es lo mismo que la disponibilidad de un servicio.

3.3 IA con human-in-the-loop

El asistente usa function calling: el modelo no ejecuta código libre, solo puede pedir herramientas declaradas. Las acciones sensibles se convierten en propuestas pendientes que el administrador confirma o rechaza. El objetivo es que la IA ayude a diagnosticar sin quitar el control.

3.4 Instalación de servicios (apt)

El panel incluye un catálogo cerrado de servicios instalables con apt: Nginx, Samba, dnsmasq, Docker, Fail2ban y Redis. No acepta nombres de paquete libres: la clave se valida contra /etc/nexus/installable.json y un helper root-owned con allowlist. Cada instalación exige confirmación y queda registrada en Auditoría.

  • En el host local del hub, el backend llama al helper mediante una regla sudoers exacta.
  • En un agente Linux, la orden viaja por el despachador y el agente llama a su propio helper.
  • Docker añade el usuario del servicio al grupo docker; hay que reiniciar nexus o nexus-agent para que el proceso lo vea.
  • Para que apt pueda escribir, las unidades relajan ProtectSystem y NoNewPrivileges; la aplicación y el agente siguen ejecutándose como usuarios no privilegiados y solo el helper tiene root.

Por qué allowlist y no un campo de paquete: instalar paquetes es una operación de root. Un campo libre convertiría el panel en una shell root; el catálogo cerrado mantiene la superficie de ataque pequeña y auditable.

3.5 Terminal SSH del panel

La pestaña Terminal abre una sesión SSH real dentro del navegador con xterm.js y un WebSocket autenticado. No hay contraseñas ni claves en el cliente: el navegador solo transporta el WebSocket; el hub abre la conexión SSH con una clave dedicada (/etc/nexus/terminal_key) y un known_hosts fijado.

  • La sesión exige cookie de administrador, token CSRF enviado en el subprotocolo csrf.<token> y el mismo origen del panel.
  • El PTY se abre como el usuario configurado en TERMINAL_SSH_USER (por ejemplo, saul_server). Si se deja vacío, la terminal queda desactivada.
  • Se cierra al cambiar de pestaña y tras TERMINAL_IDLE_SECONDS sin actividad.
  • Los comandos se ejecutan con los permisos de ese usuario; no hay una shell root implícita. Para tareas root se usa sudo y su contraseña, igual que en una SSH normal.
  • asyncssh y websockets son dependencias del hub; los assets de xterm.js están vendorizados, sin CDN.

Configuración mínima en el hub:

sudo ssh-keygen -t ed25519 -N '' -f /etc/nexus/terminal_key -C nexus-web-terminal
sudo install -d -o saul_server -g saul_server -m 0700 /home/saul_server/.ssh
sudo sh -c 'cat /etc/nexus/terminal_key.pub >> /home/saul_server/.ssh/authorized_keys'
sudo chown saul_server:saul_server /home/saul_server/.ssh/authorized_keys
sudo chmod 600 /home/saul_server/.ssh/authorized_keys
sudo sh -c 'ssh-keyscan -t ed25519 127.0.0.1 > /etc/nexus/terminal_known_hosts'
sudo chown nexus:nexus /etc/nexus/terminal_key /etc/nexus/terminal_known_hosts
sudo chmod 600 /etc/nexus/terminal_key /etc/nexus/terminal_known_hosts

Añade estas claves a /etc/nexus/nexus.env y reinicia el servicio:

TERMINAL_SSH_HOST=127.0.0.1
TERMINAL_SSH_PORT=22
TERMINAL_SSH_USER=saul_server
TERMINAL_SSH_KEY=/etc/nexus/terminal_key
TERMINAL_SSH_KNOWN_HOSTS=/etc/nexus/terminal_known_hosts
TERMINAL_IDLE_SECONDS=900

Por qué no se guarda la contraseña SSH: la clave dedicada permite auditar y revocar el acceso sin depositar secretos en el navegador. El known_hosts evita aceptar una clave de host desconocida y el CSRF impide que otro origen abra la terminal con la cookie del administrador.

4. Datos y persistencia

Nexus-Core usa SQLite para simplificar el despliegue: un solo archivo, sin servidor de base de datos, fácil de copiar y restaurar. El esquema evoluciona con migraciones versionadas.

Tabla Contenido
metric_samples Muestras de CPU, RAM, swap, disco, carga y temperatura, por host
metric_rollups Agregados por minuto y hora para históricos largos
hosts Inventario de la flota (local y agentes), estado y token
host_state Último inventario del agente (contenedores, servicios, versión)
commands Órdenes enviadas a un agente, estado, resultado y error
alert_rules / alert_events Reglas, umbrales, estados y acknowledgments
notification_channels Telegram, webhook o correo
maintenance_windows Ventanas de silencio planificadas
monitors Comprobaciones HTTP/TCP/SSL y su historial

4.1 Muestreo y agregación

  • El colector muestrea cada 5 segundos.
  • Se calculan agregados por minuto y por hora para que el histórico no crezca sin límite.
  • La retención y los rollups permiten mantener meses de tendencia con un peso pequeño.
  • El histórico se consulta por host y por rango; el CSV exporta exactamente lo que se ve.

4.2 Copias de seguridad

El script deploy/production/backup-nexus.py usa la API de backup de SQLite: crea un snapshot consistente aunque el servicio esté en marcha, comprueba PRAGMA integrity_check, incluye la configuración y rota las copias. Un backup que no se ha probado a restaurar no es un backup.

5. Multi-host: una flota, un panel

5.1 Alta de un host

  1. El administrador abre Hosts y copia el token de enrolamiento.
  2. En la máquina destino instala el agente con ese token y un nombre.
  3. El agente se enrola, recibe su token propio y empieza a latir.
  4. El hub lo muestra como un host más y permite elegirlo en el selector.

Por qué hay dos tokens: el de enrolamiento sirve para dar de alta máquinas nuevas; el token del host identifica a una máquina concreta y puede revocarse sin afectar a las demás.

5.2 Selección de host

El selector global decide qué host alimenta el Resumen y el Histórico. Las pestañas de Contenedores, Servicios, Red y Sistema ejecutan la operación en el host seleccionado:

  • Si es el host local del hub, se usan los módulos locales.
  • Si es un agente, la orden viaja por el despachador (POST /api/hosts/{id}/command) y el agente la ejecuta con una allowlist de herramientas.

5.3 Límites del agente

El agente puede ejecutar: métricas, Docker (listar, logs, stats, desplegar, eliminar, prune), servicios (listar, detalle, logs, acciones), red (interfaces, escaneo) y sistema (puertos, actualizaciones, SMART). No ejecuta código arbitrario. Un host Windows no tiene systemd ni Docker accesible con la misma semántica: la UI muestra un aviso claro en lugar de fingir.

6. Seguridad

La seguridad no es una pestaña: es una propiedad del diseño. Estas son las capas, de fuera hacia dentro.

6.1 Capas de protección

Capa Medida Por qué
Borde TLS (Caddy o Cloudflare Tunnel) Cifra el tráfico y evita credenciales en claro
Red Firewall: solo SSH de entrada; el resto sale El hub no necesita puertos abiertos hacia Internet
Aplicación Cookies Secure + HttpOnly + SameSite, CSRF Evita robo de sesión y peticiones cruzadas
Identidad Contraseña fuerte + 2FA TOTP + códigos de recuperación Una contraseña filtrada no basta para entrar
Sesiones Caducidad por inactividad y absoluta Limita el daño de un equipo desatendido
Fuerza bruta Rate limiting por usuario e IP Frena ataques automatizados

Privilegios Servicio como usuario no root + helpers sudo acotados Un fallo en la app no es root directo

6.2 Autenticación y 2FA

  • La contraseña se almacena con un hash fuerte (Argon2id) y nunca se registra.
  • El login tiene límite de intentos por usuario y por IP.
  • 2FA TOTP: Google Authenticator (o cualquier app compatible) genera un código de 6 dígitos cada 30 segundos. El servidor guarda el secreto y verifica una ventana corta.
  • Códigos de recuperación: se muestran una sola vez, se guardan hasheados y sirven si se pierde el móvil. Deben guardarse fuera del teléfono.
  • El panel exige el código en el mismo formulario de login, no en una pantalla opcional.

Por qué TOTP y no SMS: TOTP no depende de la operadora, funciona sin cobertura y no expone el número de teléfono a terceros. Es el estándar de las cuentas profesionales.

6.3 Sesiones, CSRF y cookies

Las sesiones caducan por inactividad (30 minutos por defecto) y por tiempo absoluto (8 horas). Cada petición que modifica datos exige un token CSRF. La cookie de sesión se marca Secure cuando el panel se sirve por HTTPS; sin HTTPS, el navegador no la envía y el login no persiste, lo que evita un falso sentido de seguridad.

6.4 Superficie de ataque y privilegios

  • La aplicación corre como usuario nexus, no como root.
  • Las operaciones que requieren privilegios pasan por helpers concretos con reglas sudo validadas (visudo) y una lista blanca de unidades.
  • El socket de Docker es potente: montarlo da un privilegio equivalente a root sobre el host. Por eso el despliegue con Docker se documenta como opción de laboratorio y se recomienda el servicio nativo en producción.
  • El instalador apt solo acepta claves del catálogo; el helper root-owned valida la clave y ejecuta apt sin recibir comandos del panel. Las unidades relajan el sandbox para que apt escriba, pero la aplicación y el agente siguen como usuarios sin privilegios.
  • El escaneo de red se limita a rangos privados y requiere autorización.

6.5 Secretos y configuración

  • .env y los tokens nunca se suben al repositorio; el repositorio público solo contiene ejemplos con marcadores.
  • El token de enrolamiento se puede rotar; los hosts ya enrolados conservan su token propio.
  • La configuración de producción vive en /etc/nexus/nexus.env con permisos 0600.
  • Los backups incluyen secretos: se guardan cifrados o fuera del servidor y con permisos 0600.

6.6 Despliegue en Internet

Dos opciones habituales:

  1. Cloudflare Tunnel: cloudflared abre una conexión saliente y Cloudflare publica el panel con HTTPS. Un Quick Tunnel es gratis, no requiere cuenta y cambia de URL; sirve para pruebas. Un Named Tunnel con dominio y Cloudflare Access es la opción estable y añade login por email antes de llegar al panel.
  2. VPS con Caddy: el hub escucha en 127.0.0.1:8000, Caddy termina TLS y añade HSTS y cabeceras de seguridad. El firewall solo permite SSH, 80 y 443.

En ambos casos el panel no debe escuchar en 0.0.0.0 cuando se publica; se enlaza a localhost y el proxy/túnel hace de puerta.

7. Redes

7.1 Escaneo de la red local

El escaneo busca hosts activos en una subred privada (RFC 1918). Usa nmap si está disponible y, si no, un barrido con tabla ARP como respaldo. El resultado muestra IP, estado, MAC y nombre. Solo debe usarse en redes propias o con autorización expresa.

Por qué se limita a rangos privados: escanear redes ajenas es intrusión. La herramienta educativa debe enseñar el límite, no solo la técnica.

7.2 Agentes y NAT

El agente no necesita IP fija ni puertos abiertos: inicia una conexión HTTPS saliente y mantiene un long-poll. Funciona detrás de NAT, en una VM de aula o en una Raspberry Pi. El hub solo necesita ser alcanzable por el agente (por LAN o por el túnel).

7.3 Docker y puertos

El panel muestra el estado de los contenedores y los puertos publicados. El despliegue usa una lista blanca de imágenes y un límite de contenedores gestionados. Es una decisión de seguridad: no se permite desplegar cualquier imagen desde el panel.

7.4 Cabeceras de proxy y HTTPS

Cuando hay un proxy (Caddy, Cloudflare), uvicorn debe confiar en las cabeceras reenviadas (--proxy-headers --forwarded-allow-ips=127.0.0.1). Así la IP del cliente, el esquema HTTPS y las cookies Secure se comportan correctamente. Sin esa confianza, el panel vería todo el tráfico como localhost.

8. Instalación y operación

8.1 Hub nativo (recomendado)

sudo apt install -y git python3 python3-venv
git clone <repo> nexus-core
cd nexus-core
sudo bash deploy/install.sh

El instalador crea el usuario nexus, los directorios, el entorno virtual, los helpers, la unidad systemd y el token de primer arranque. El panel escucha en el puerto 8000.

8.2 Primer arranque

sudo cat /var/lib/nexus/setup_token

Se abre el panel, se pega el token, se crea el administrador y se guarda la contraseña en un gestor. Después se activa el 2FA y se guardan los códigos de recuperación.

8.3 Agente en otra máquina

sudo bash deploy/agent/install-agent.sh \
  --hub https://nexus.example.com \
  --enroll-token '<TOKEN>' \
  --name "vm-aula-01"

El agente se instala como servicio systemd, se enrola y empieza a latir. No hay que abrir puertos en la máquina vigilada.

8.4 Backups y actualización

sudo systemctl enable --now nexus-backup.timer
sudo systemctl start nexus-backup.service

Actualizar el hub:

cd nexus-core && git pull
sudo bash deploy/update.sh

8.5 Diagnóstico rápido

Síntoma Comprobación
El panel no carga systemctl status nexus; curl http://127.0.0.1:8000/api/health
Un host no aparece systemctl status nexus-agent; token, URL del hub y salida HTTPS
El túnel da 530/502 El túnel no está conectado o el hub no escucha en localhost
La sesión no persiste HTTPS y cookie Secure; usa la URL HTTPS, no HTTP
Docker no lista El usuario del servicio no está en el grupo docker o el socket no existe

9. Laboratorios para el aula

Todos los ejercicios se hacen en una red de laboratorio propia y con autorización. No se escanean redes ajenas ni se usan credenciales reales.

Laboratorio 1 — Arquitectura

Dibuja el flujo navegador → hub → agente. Identifica qué viaja por HTTPS y qué por long-poll. Pregunta: ¿por qué el agente no necesita abrir el puerto 22?

Laboratorio 2 — Monitorizar una VM

Instala un agente en una VM del aula y compárala con el host local. Objetivo: ver dos hosts en el selector y entender el concepto de flota.

Laboratorio 3 — Alerta de disco

Crea una regla de disco > 80 % con recuperación al 70 % y duración 5 minutos. Llena un archivo temporal hasta cruzar el umbral. Observa: cuándo se abre, cuándo se cierra y qué queda en Auditoría.

Laboratorio 4 — Servicio caído

Detén un servicio no crítico del laboratorio y comprueba el estado, los logs y la acción de reinicio. Pregunta: ¿qué privilegios necesita el panel y por qué no corre como root?

Laboratorio 5 — Inventario de red

Escanea la subred del laboratorio. Compara el resultado de nmap con el respaldo ARP. Pregunta: ¿qué diferencia hay entre un host que responde a ping y uno que bloquea ICMP?

Laboratorio 6 — 2FA y recuperación

Activa TOTP, cierra sesión y entra con el código. Después usa un código de recuperación. Pregunta: ¿por qué el servidor guarda los códigos de recuperación hasheados?

Laboratorio 7 — Backup y restauración

Ejecuta el script de backup, inspecciona el archivo y restaura en una copia de la base. Objetivo: comprobar integridad y entender que un backup sin restauración no es una garantía.

Laboratorio 8 — Publicación segura

Publica el panel con un túnel o un proxy TLS en el laboratorio. Verifica HSTS, cookies Secure y que el puerto 8000 no es accesible desde fuera. Pregunta: ¿qué añade Cloudflare Access?

11. Glosario

  • Hub: servidor central que recibe telemetría y reparte órdenes.
  • Agente: proceso en una máquina vigilada que envía métricas y ejecuta herramientas.
  • Long-poll: petición HTTP que el servidor mantiene abierta hasta que hay una orden.
  • TOTP: código temporal de 6 dígitos basado en tiempo (Google Authenticator).
  • CSRF: ataque que fuerza a un navegador autenticado a enviar una petición no deseada.
  • TLS: cifrado de la conexión (HTTPS).
  • Reverse proxy: servidor que recibe el tráfico y lo reenvía al backend (Caddy, Nginx).
  • CIDR: notación de subred, por ejemplo 192.0.2.0/24.
  • NAT: traducción de direcciones que permite salir a Internet sin IP pública.
  • Allowlist: lista explícita de lo permitido (herramientas, imágenes, unidades).
  • Rollup: agregado de datos para conservar histórico sin crecer indefinidamente.
  • SSRF: forzar al servidor a hacer peticiones a destinos internos no previstos.
  • Human-in-the-loop: la IA propone y una persona confirma.

12.4 Buenas prácticas de operación

  • Cambia la contraseña inicial y activa 2FA antes de publicar el panel.
  • Usa HTTPS; nunca publiques el puerto 8000 directamente.
  • Guarda el token de enrolamiento como un secreto y rótalo si se filtra.
  • Prueba la restauración de backups, no solo su creación.
  • Mantén el servidor actualizado y con el firewall cerrado salvo lo imprescindible.
  • Revisa la auditoría cuando ocurra algo raro.
  • No escanees redes sin autorización.
  • Trata las respuestas de la IA como propuestas, no como órdenes.
